# Identity

This page covers the SDK identity model: layered storage, capability detection, session rotation, and the `identify` / `reset` lifecycle.

The full architectural rationale is in [SDK Standards / Browser Identity Lifecycle](../architecture/10-sdk-standards.md#browser-identity-lifecycle); this page is the operator-eye view.

## Identity fields

Every event carries an `identity` block:

```ts
interface EnvelopeIdentity {
  anonymous_id: string | null;
  session_id: string | null;
  customer_id: string | null;
  device_id: string | null;   // currently always null
}
```

- `anonymous_id` is generated and persisted by the SDK on first activity. It survives across visits when persistent storage is available.
- `session_id` is generated by the SDK and rotates after 30 minutes of inactivity (Web). The Node SDK rotates on explicit `reset()` only.
- `customer_id` is set by `identify(customerId, traits?)` and cleared by `reset()`. `identify()` also emits `user.identified`, whose properties are the traits; the identity stage merge-patches them into the profile store.
- `device_id` is always `null` today.

The ingester does **not** rewrite these fields. Identity resolution (linking anonymous IDs to customers across devices) is a downstream processor concern, not an SDK concern. See [Architecture / Identity Resolution Coupling](../architecture/10-sdk-standards.md#identity-resolution-coupling).

## Web SDK: layered persistence

The Web SDK picks the strongest available storage layer at construction time. The doctrinal order is:

```text
first-party cookie     -> stronger browser continuity signal
localStorage mirror    -> normal browser continuity signal
sessionStorage         -> weaker session-only signal
in-memory              -> weakest transient signal
```

Rules baked into the SDK:

- First-party cookie is preferred when available. No third-party cookies. No fingerprinting.
- When localStorage is also available and a non-localStorage layer is canonical, `anonymous_id` is mirrored into localStorage as a redundant fallback.
- Capability detection runs once at construction; `getCapability()` returns the snapshot.
- The SDK records the storage layer used as diagnostic context. The downstream identity resolver treats storage layer as evidence quality.

### Configuring the cookie layer

```ts
const sdk = await PolarisWebSdk.create({
  endpoint: "https://ingest.polaris.internal/v1/events",
  apiKey: "POLARIS_API_KEY",
  source: { id: "checkout-app" },
  identity: {
    cookie: {
      name: "polaris_id",          // default
      domain: ".example.com",      // share across subdomains
      path: "/",                   // default
      maxAgeSeconds: 60 * 60 * 24 * 30 * 13, // default ~13 months
      sameSite: "Lax",             // default — "None" is intentionally not exposed
      secure: undefined,           // auto: true on https, false otherwise
    },
  },
});
```

The SDK uses a single cookie and JSON-encodes the identity payload inside it. Do not configure one cookie per identity field.

`SameSite=None` is not exposed because third-party cookie use is forbidden by [SDK Standards / Layered Browser Persistence](../architecture/10-sdk-standards.md#layered-browser-persistence). The default `Lax` covers the standard same-site flows.

### Overriding the layer order

The default order is `["cookie", "localStorage", "sessionStorage", "memory"]`. Override only with a clear reason:

```ts
const sdk = await PolarisWebSdk.create({
  endpoint: "https://ingest.polaris.internal/v1/events",
  apiKey: "POLARIS_API_KEY",
  source: { id: "embedded-widget" },
  identity: {
    // E.g., a widget that explicitly opts out of cookies for legal reasons.
    storageOrder: ["localStorage", "sessionStorage", "memory"],
  },
});
```

If you remove `"memory"` from the order, the SDK still falls back to memory at runtime — memory is always available; the layered store treats it as the last-resort. Skipping memory in `storageOrder` just signals intent.

## Web SDK: capability detection

The SDK probes each layer at construction and exposes the result:

```ts
const capability = sdk.getCapability();
// {
//   available: ["cookie", "localStorage", "sessionStorage", "memory"],
//   primary: "cookie",
//   degraded: false,
//   webview: false,
//   secureContext: true,
// }
```

- `available` is the list of layers that responded to a synchronous probe.
- `primary` is the highest-priority layer the SDK selected for writes.
- `degraded` is `true` when the SDK ended up on `sessionStorage` or `memory` (typical for private-mode browsing, locked-down Safari, ad WebViews).
- `webview` is `true` when the SDK detected an embedded-browser user agent.
- `secureContext` is `true` when the page was loaded over HTTPS. Drives the `Secure` cookie flag.

The `degraded` flag is the operator's signal: an event marked `degraded: true` should be weighted as a weaker continuity signal downstream.

## Web SDK: session rotation

Sessions rotate after 30 minutes of inactivity:

- Every `track()` and `identify()` touches the activity clock.
- A `getAnonymousId()` / `getSessionId()` read also triggers an inactivity check.
- A hydrated identity older than 30 minutes is rotated immediately, before the first call returns.

Campaign parameter changes do **not** rotate the session — see [Identity / Session Lifecycle](../architecture/10-sdk-standards.md#session-lifecycle). Campaign IDs travel in `context.campaign`.

Override the inactivity threshold (rare):

```ts
const sdk = await PolarisWebSdk.create({
  endpoint: "https://ingest.polaris.internal/v1/events",
  apiKey: "POLARIS_API_KEY",
  source: { id: "checkout-app" },
  identity: {
    sessionInactivityMs: 15 * 60 * 1000, // 15 minutes
  },
});
```

## Web SDK: anonymous-id continuity

`anonymous_id` persists across reloads as long as the underlying layer survives. On a cookie-or-localStorage browser, this can be months (default cookie max-age is ~13 months). On a session-only or memory-only fallback, the ID lives only as long as the tab/session does.

`reset()` rotates `anonymous_id` by default. To preserve continuity across logout — for products that distinguish session boundaries but treat logout as same-user:

```ts
sdk.reset({ anonymous: false });
```

## Web SDK: introspection helpers

```ts
sdk.getIdentityManager();    // direct access to the IdentityManager
sdk.getCapability();         // capability snapshot
sdk.getDiagnostics();        // capability + currentLayer + lastActivityAt
sdk.getEnvelopeIdentity();   // current identity shaped for an envelope
```

`getEnvelopeIdentity()` is what `track()` calls internally on every event. The returned object is a snapshot — calling `identify()` later does not retroactively change a previously-returned object.

## Node SDK: identity model

The Node SDK persists identity in memory for the lifetime of the SDK instance. There is no file-backed default today.

> Note: the shipped Node SDK does **not** implement file-backed identity persistence. Identity lives in the SDK instance and is lost on process restart. Operators that need durability should either (a) inject pre-minted identity values via `options.identity`, or (b) wait for a durable queue adapter to land and emit identity through the application's own state store.

### Default behaviour

- The constructor mints `anonymous_id` and `session_id` (UUIDv7 with `anon_` / `sess_` prefixes).
- `identify(customerId, traits?)` sets `customer_id` in place **and emits `user.identified`** carrying the traits. The identifier is set first, so that event carries both `anonymous_id` and `customer_id` — the overlap the resolver binds into one profile.
- `reset()` clears `customer_id`, rotates `session_id`, and (by default) rotates `anonymous_id`.
- Identity does not automatically rotate on inactivity in the Node SDK. Backends usually run one SDK instance per process, so session rotation is operator-driven.

### Caller-supplied identity defaults

```ts
const polaris = new PolarisNodeSdk({
  endpoint: "https://ingest.polaris.internal/v1/events",
  apiKey: process.env.POLARIS_API_KEY!,
  source: { type: "backend", id: "checkout-api" },
  identity: {
    anonymous_id: null,            // backend has no anonymous concept
    session_id: null,
    customer_id: null,
    device_id: null,
  },
});
```

For most backend producers, the persistent identity is left null and a per-event identity is supplied:

```ts
await polaris.track(
  "payment.approved",
  { amount: 12990, currency: "BRL" },
  {
    identity: { customer_id: "cus_123" },
  },
);
```

### Reading identity

```ts
const ids = polaris.getIdentity();
// {
//   anonymous_id: "anon_018f1b...",
//   session_id: "sess_018f1b...",
//   customer_id: null,
//   device_id: null,
// }
```

`getIdentity()` returns a frozen snapshot. Use it to correlate Polaris events with your own logs or traces without firing a Polaris event just to inspect.

## Identity is evidence, not truth

Storage IDs are *evidence* of continuity, not authoritative identity. Authoritative links between `anonymous_id` and `customer_id` come from explicit overlap on a single event:

```text
anonymous_id + customer_id on same event
session_id + customer_id on same event
documented business identifier + customer_id
```

The SDK creates that overlap automatically by stamping the active `anonymous_id` and `session_id` on every event including events that fire after `identify(customer_id)`. The downstream identity resolver consumes that overlap.

See [SDK Standards / Identity Resolution Coupling](../architecture/10-sdk-standards.md#identity-resolution-coupling).
