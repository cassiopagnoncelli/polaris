# Polaris PostgreSQL Migrations

This directory holds the SQL-first migration history for the Polaris control
plane.

## Why this directory exists

Polaris is **file-heavy and database-light**. PostgreSQL stores only mutable
runtime/control state — API keys, sources, destination instance settings,
processor runs, replay jobs, delivery records, audit records, operator tokens.
Semantic platform truth (event schemas, destination mappings, processor logic,
ClickHouse DDL) lives in versioned code, not in PostgreSQL.

See:

- `docs/architecture/02-control-plane.md` — what PostgreSQL is allowed to own
- `docs/architecture/09-engineering-standards.md` — "PostgreSQL Migrations" section

## Tooling

- **Migration runner:** [dbmate](https://github.com/amacneil/dbmate) (installed
  as a workspace devDependency in `packages/shared-db/`).
- **File format:** plain SQL. Each file has a `-- migrate:up` and
  `-- migrate:down` block.
- **History table:** dbmate's default `schema_migrations`. No analog is
  created.
- **Filename convention:** dbmate's default, `YYYYMMDDHHMMSS_short_slug.sql`.

Migration timestamps are UTC and generated by dbmate; the slug is a short,
imperative description (`create_api_keys`, `add_source_id_index`).

dbmate is invoked through `pnpm` scripts at the repo root. You do **not** need
to install dbmate globally.

## Connection settings

By default, scripts target the local compose stack:

```text
postgres://polaris:polaris@localhost:5432/polaris?sslmode=disable
```

Override by exporting `DATABASE_URL` before running a script:

```bash
export DATABASE_URL="postgres://polaris:polaris@localhost:5432/polaris?sslmode=disable"
pnpm db:status
```

`docker-compose.yml` pins the compose stack to the same `polaris/polaris/polaris`
defaults, so a freshly started stack accepts the default URL above without
configuration.

A starter env file is available at `db/.env.example`. The simplest way to
use it is to source it into the shell that runs the script:

```bash
set -a; source db/.env.example; set +a
pnpm db:migrate
```

For a longer-lived local override, export `DATABASE_URL` in your shell rc
or your IDE run config. Do not commit a `.env` file containing credentials.
The repository's gitignore policy for `.env*` is owned by task P11-006;
until then, treat any `.env` you create as private and add it locally with
`git update-index --skip-worktree` if needed.

## Common workflows

All commands are run from the repository root and are thin wrappers around
dbmate.

### Apply pending migrations

```bash
pnpm db:migrate
```

Applies every migration the local database has not yet applied. Idempotent — a
clean re-run is a no-op.

### Roll back the most recent migration

```bash
pnpm db:rollback
```

Runs the `-- migrate:down` block of the most recently applied migration.
Polaris migrations are expected to be reversible; if a migration cannot be
reversed cleanly, document the reason in the file header before merging.

### Inspect migration status

```bash
pnpm db:status
```

Shows applied and pending migrations.

### Create a new migration

```bash
pnpm db:create <short_slug>
```

Generates `db/migrations/<timestamp>_<slug>.sql` with empty `migrate:up` and
`migrate:down` blocks. Fill both blocks before committing.

### Reset the local database

There is no dedicated `db:reset` script. Reset the local database by wiping
the compose volume and reapplying migrations:

```bash
docker compose down -v
docker compose up -d postgres
pnpm db:migrate
```

This is local-only. Never run `down -v` against shared environments.

## Authoring rules

1. **One change per migration.** A migration creates one table, adds one
   column, or backfills one set of rows. Reviewers should be able to read a
   single file and understand the change.
2. **Always write both `migrate:up` and `migrate:down`.** A missing down block
   is a merge blocker unless the migration header explicitly documents the
   reason (irreversible data migration, etc.).
3. **No semantic platform truth in SQL.** Migrations do not encode event
   schemas, destination mapping rules, processor logic, or anything that
   defines what a Polaris event means. Those live in code.
4. **No application data seeds in migrations.** Seeding is a separate
   workflow.
5. **Use `timestamptz`, not `timestamp`.** Polaris timestamps are UTC at all
   storage boundaries.
6. **Use UUIDv7 columns as `uuid`.** Generation happens in application code
   (Node `uuidv7` or equivalent); do not call Postgres-side UUID helpers.
7. **Reference file-defined objects by stable ID, not by reproducing their
   semantics.** For example, store `consumer_name` + `consumer_version` on a
   destination instance row; do not store the mapper code.
8. **Run migrations forward, never edit applied files.** Once a migration has
   landed on `main`, fix mistakes with a follow-up migration. The history
   table is the source of truth.

## What goes here later (not now)

The current migration file (`20260512000001_bootstrap.sql`) only pins the
database timezone to UTC. Application tables ship with the tasks that own
them:

| Tables                              | Owner task        |
| ----------------------------------- | ----------------- |
| `api_keys`, `sources`               | P6-002 / P6-003   |
| `destination_instances`             | P6-004            |
| `processor_runs`                    | P6-005 / P8-001   |
| `replay_jobs`                       | P7-001            |
| `delivery_records`                  | P9-001 / P9-007   |
| `audit_records`, `operator_tokens`  | P6-006 / P6-007   |
| `topic_isolations`                  | P11-008           |
| `identity_links`                    | P8-002            |

Each owning task is responsible for shipping the migration that creates its
tables and any necessary indexes. This task ships only the mechanism.
